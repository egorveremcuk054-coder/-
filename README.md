# Спасатель против саботажников — логика игры

«Мозг» асимметричной игры на TypeScript: класс `Game` с чистой игровой логикой, без сети, графики и таймеров.
Спасатель присматривает за подопечными `w1…wN`. Среди них прячутся саботажники, которые устраивают несчастные случаи.
У спасателя есть несколько секунд, чтобы помочь, и он должен вычислить, кто саботажник.

## Как запустить

Нужен Node.js 20.19+ или 22.12+ (нижняя граница — требование Vite, на котором работает Vitest).
GitHub Actions прогоняет тесты и проверку типов на Node 20, 22 и 24 (`.github/workflows/test.yml`).

```bash
npm install
npm test
```

Дополнительно:

```bash
npm run typecheck   # проверка типов в строгом режиме (tsc --noEmit)
npm run test:watch  # тесты в режиме наблюдения
```

## Как устроено

```
src/
  balance.ts   все числа баланса: defaultBalance, склейка с переопределениями и проверка
  game.ts      класс Game: вся игровая логика
  types.ts     публичные типы: Result, FailReason, GameEvent, PublicState
  rng.ts       детерминированный генератор mulberry32 (для тестов и сервера, в логике не используется)
  index.ts     точка входа: реэкспорт всего перечисленного
tests/
  helpers.ts         генератор с заданными значениями, сборка игры с нужными саботажниками, случайные сценарии
  setup.test.ts      создание игры, выбор саботажников, баланс и его проверка
  incident.test.ts   startIncident: задержка, кулдауны, цели, гибель ровно в дедлайн
  rescue.test.ts     rescue: последняя миллисекунда окна, кулдаун спасателя
  accuse.test.ts     accuse: верные и неверные обвинения, отказы
  timeline.test.ts   конец раунда, порядок событий в один момент, большой шаг = много маленьких
  hidden-info.test.ts публичное состояние не выдаёт саботажников
  determinism.test.ts один генератор — одна партия; игра не трогает Math.random, Date.now, таймеры
  source-rules.test.ts статическая проверка исходников: нет запрещённых API и магических чисел в game.ts
.github/workflows/test.yml  тесты и проверка типов на Node 20, 22, 24
```

**Время.** Игра не знает про реальное время: оно приходит только через `update(dtMs)`.
Внутри `update` работает маленький событийный цикл: пока игра не закончилась, берётся ближайшее событие
не позже конца шага — гибель по дедлайну несчастного случая или конец раунда, — время переводится ровно
на момент этого события, событие обрабатывается, и цикл повторяется. Поэтому `update(60_000)` даёт ровно
то же, что 60 вызовов `update(1000)`: каждое событие обрабатывается в свой точный момент, независимо от
того, какими шагами шли. В тестах это проверяется и на ручных сценариях, и на 300 случайных сценариях,
которые прогоняются одним шагом, шагами по 1000 мс, по 1 мс и шагами случайной длины.

**Случайность.** Генератор передаётся в конструктор и вызывается в двух местах: при создании игры
(частичная перетасовка Фишера — Йетса, по одному вызову на саботажника) и при каждом *успешном*
`startIncident` (выбор вида). Отказы генератор не трогают, поэтому последовательность случайных чисел
зависит только от успешных действий.

**Баланс.** Все числа лежат в `src/balance.ts`. В `game.ts` нет других чисел, кроме 0 и 1, — это проверяет
тест `source-rules.test.ts`. Свой баланс передаётся частично: `new Game({ rng, balance: { incidentWindowMs: 500 } })`,
остальное берётся из `defaultBalance`. Бессмысленный баланс (например, саботажников не меньше, чем подопечных)
сразу даёт `RangeError`.

**Проверка самих тестов.** Чтобы убедиться, что тесты ловят ошибки, а не просто проходят, в `game.ts` по одной
вносились 23 типичные ошибки: граница времени сдвинута на 1 мс, смерть обрабатывается в конце шага, а не в свой
момент, саботажник попадает в публичное состояние, генератор игнорируется или тратится на отказах, пороги
поражения сравниваются через `>` вместо `>=` и т. п. 22 ошибки тесты поймали. Оставшаяся — удаление проверки
`if (this.outcome) return` в `update` — не меняет поведения (цикл и так не идёт после конца игры), то есть
ошибкой не является.

**Скрытая информация.** Внутреннее состояние (кто саботажник, кто устроил случай) хранится в приватных полях.
`getPublicState()` каждый раз собирает новый объект только из того, что можно показать спасателю.
Тест `hidden-info.test.ts` играет одну и ту же партию с разными саботажниками и проверяет, что спасатель
видит одинаковые состояния и события, пока игра не закончилась.

### PublicState

| Поле | Что значит |
|---|---|
| `time` | Сколько миллисекунд прошло с начала раунда |
| `timeLeftMs` | Сколько осталось до конца раунда |
| `wards` | Подопечные по порядку: `{ id, status, accused }`. `status` — `alive`, `dead` или `caught`; `accused` — спасатель уже обвинял этого подопечного |
| `incidents` | Активные несчастные случаи в порядке начала: `{ wardId, kind, startedAt, remainingMs }`. Кто устроил случай, не указано |
| `deaths` | Сколько подопечных погибло |
| `wrongAccusations` | Сколько было неверных обвинений |
| `rescueCooldownLeftMs` | Сколько осталось до конца кулдауна спасателя, 0 — можно спасать |
| `isOver` | Игра закончилась |
| `winner` | `rescuer`, `saboteurs` или `null`, пока игра идёт |
| `endReason` | Причина конца, как в событии `game_over`, или `null` |
| `saboteurIds` | Идентификаторы саботажников. `null`, пока игра идёт; после конца — список |

### Пример

```ts
import { Game, createSeededRng } from './src';

const game = new Game({ rng: createSeededRng(42) });
game.update(10_000);
game.startIncident('w3', 'w5'); // вызывает сервер от имени игрока-саботажника
game.rescue('w5');              // от имени спасателя
const state = game.getPublicState(); // отправляется спасателю
const events = game.drainEvents();   // события с последнего вызова
```

## Допущения

Решения, которые я принял сам там, где условие допускало разные толкования.

**Границы времени — включительно.**
- Начать несчастный случай можно ровно в момент `initialSabotageDelayMs`; раньше — `too_early`.
- Кулдауны саботажника и спасателя заканчиваются ровно в момент «начало + кулдаун»: в этот момент действие уже разрешено.
- Подопечный погибает ровно в момент «начало + `incidentWindowMs`». `update` обрабатывает дедлайны включительно, поэтому в этот момент несчастного случая уже нет и `rescue` отвечает `no_active_incident`.
- Раунд заканчивается ровно в момент `roundDurationMs`.

**Порядок проверок.** Если не выполнено несколько условий, возвращается первая причина по порядку:
- `startIncident`: `game_over` → `unknown_ward` (сначала саботажник, потом цель) → `not_saboteur` → `ward_not_alive` (саботажник уже разоблачён) → `too_early` → `sabotage_cooldown` → `target_is_saboteur` → `ward_not_alive` (цель мертва) → `incident_already_active`.
- `rescue`: `game_over` → `unknown_ward` → `no_active_incident` → `rescue_cooldown`.
- `accuse`: `game_over` → `unknown_ward` → `already_accused` → `ward_not_alive`.

**Новая причина отказа `target_is_saboteur`.** Условие запрещает устраивать несчастный случай саботажнику, но подходящей причины в списке нет. Я добавил в `FailReason` значение `target_is_saboteur` (в том числе для попытки устроить случай самому себе). Существующие названия не менял.

**Разоблачённый саботажник** больше не может начинать несчастные случаи: `ward_not_alive`, потому что его статус `caught`, а не `alive`.

**Обвинения.**
- Повторное обвинение любого уже обвинённого подопечного — `already_accused`, даже если он с тех пор погиб или был разоблачён. Эта проверка идёт раньше проверки статуса.
- Неверно обвинённый остаётся `alive`: его можно снова сделать целью несчастного случая, и он может погибнуть. В публичном состоянии у него `accused: true`.
- Неверное обвинение не отменяет несчастный случай на обвинённом.
- Верное обвинение отменяет **все** активные несчастные случаи этого саботажника (их может быть несколько, если в балансе кулдаун меньше окна спасения). События идут в порядке `saboteur_caught` → `incident_cancelled` → `game_over`.

**Несколько событий в один момент.**
- Несколько смертей в один момент обрабатываются в порядке начала несчастных случаев.
- Игра заканчивается на первом событии, которое решает исход. Если в тот же момент должен погибнуть ещё кто-то, это уже не происходит: после конца игры ничего не обрабатывается.
- Смерть в момент `roundDurationMs` обрабатывается раньше конца раунда (так требует условие). Если она не решает исход, сначала приходит `ward_died`, потом `game_over` с `time_up`.
- Несчастный случай, дедлайн которого позже конца раунда, никого не убивает.

**Время после конца игры.** Условие говорит и «`game.time` равно сумме всех `dtMs`», и «после конца игры время останавливается». Я считаю второе важнее: `game.time` равно моменту конца игры, даже если последний шаг `update` был длиннее.

**Шаг времени.** `dtMs` должно быть конечным числом ≥ 0, иначе `RangeError` (в том числе после конца игры: это ошибка вызывающего кода, а не игровое действие). Дробные значения разрешены, но точное равенство «большой шаг = много маленьких» гарантировано для целых миллисекунд: дробные складываются с погрешностью плавающей точки.

**Генератор.** Если `rng()` вернул число вне `[0, 1)` или `NaN`, игра бросает `RangeError`, а не выбирает что-то молча.

**Саботажники не гибнут:** их нельзя сделать целью, поэтому `deaths` считает только обычных подопечных.

**Где проходит граница «сервер — клиент».** Методы `startIncident`, `rescue`, `accuse` вызывает сервер от имени авторизованного игрока. Ответ `not_saboteur` сам по себе раскрывает роль, поэтому сервер не должен давать спасателю вызывать `startIncident` от чужого имени. Как сервер сообщает саботажникам их роль — вне рамок задания; отдельного метода для этого нет, чтобы роли нельзя было случайно отдать спасателю.

**Импорт.** `Game` лежит в `src/game.ts`, баланс — в `src/balance.ts`, всё вместе реэкспортируется из `src/index.ts`.
